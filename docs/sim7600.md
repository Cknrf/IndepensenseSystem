# SIM7600G-H — cellular data + GPS

The Waveshare SIM7600G-H 4G Dongle provides two capabilities for IndepenSense:

- **Cellular data** (LTE via a data-only SIM) — a fallback network when WiFi is
  unavailable, so alerts and status still reach the guardian dashboard when the
  user walks out of a home/university network.
- **GPS / GNSS** — the same module includes a multi-constellation GNSS
  receiver (GPS + GLONASS + BeiDou + Galileo) that streams NMEA sentences on
  a dedicated serial port. Requires a separate external GPS antenna
  (see below).

## Status reference

| Item | Value |
|---|---|
| Hardware | Waveshare SIM7600G-H 4G Dongle (USB) |
| USB vendor:product | `1e0e:9001` (SimTech) |
| Kernel drivers | `option` (5x serial ports) + `qmi_wwan` (network) |
| Modem manager | ModemManager + NetworkManager (Pi OS Trixie stock stack) |
| Data path | QMI over `/dev/cdc-wdm0` → `wwan0` network interface |
| GPS port | `/dev/serial/by-id/...-if01-port0` (NMEA stream at 115200 baud). Currently `ttyUSB1`, but that number moves when the modem re-enumerates — use the `by-id` path |
| AT command ports | interfaces 2 and 3 — `/dev/serial/by-id/...-if02-port0` and `...-if03-port0` (currently `ttyUSB2`/`ttyUSB3`) |
| Test SIM | Globe/GOMO (data plan) |
| APN | `internet.globe.com.ph` |
| Route metrics | WiFi 600 (preferred), cellular 700 (fallback) |

**On `/dev/ttyUSBn` anywhere below.** The commands in this document name
numbered ports because they are typed by hand, and the numbers are what
you will see today. They are not stable: the kernel assigns `ttyUSBn` in
enumeration order and this modem re-enumerates — a dmesg two seconds
apart shows it drop `ttyUSB2`-`ttyUSB5` and return as `ttyUSB0`-`ttyUSB4`.
ModemManager's index moves for the same reason, which is why `mmcli -m 0`
eventually answers "couldn't find modem". Before a manual session, run
`ls -l /dev/serial/by-id/` and read the number off the interface you
want. Anything committed to code uses the `by-id` path instead.

## Why the dongle and not the HAT

Waveshare offers both a HAT and a USB dongle version of the SIM7600G-H. The
dongle was chosen because the Pi's 40-pin GPIO header is already fully used
by other sensors (DYP-A22 ultrasonic sensors on UART0 and UART4, MPU6050 IMU
on I2C1). A HAT would physically cover the header and block wire access to
those sensors. The USB form factor also makes cellular a hot-swappable
component during development.

## Why the modem stack was chosen this way

- **QMI over PPP.** The kernel exposes the SIM7600's modem interface as a
  QMI (Qualcomm MSM Interface) device (`/dev/cdc-wdm0`) rather than as a PPP
  serial link. QMI is faster to bring up, more resilient, and is the modern
  Linux default for LTE modems.
- **ModemManager + NetworkManager over direct `qmicli` + `udhcpc`.**
  ModemManager provides a nice abstraction (`mmcli`, `nmcli`) and
  auto-reconnects on failure. Direct QMI would work but requires more shell
  scripting and lacks the reboot-persistence NetworkManager gives for free.

## Prerequisites

The Pi OS Trixie kernel already includes the `option` and `qmi_wwan` drivers.
Only ModemManager needs installing — it is not part of the default Pi OS
image:

```bash
sudo apt update
sudo apt install -y modemmanager
mmcli --version
```

A **data-only SIM** (Globe, Smart, DITO, or GOMO) with an active plan.

An **external GPS antenna** — the Waveshare package ships **only the LTE
antenna**. A separate active GNSS antenna with SMA connector is required for
GPS to obtain a fix.

## Verify hardware detection

Plug the dongle into any USB port on the Pi (USB-A recommended for reliable
power delivery). Confirm the kernel sees it:

```bash
lsusb | grep -i 'sim\|1e0e'
# Expected: "1e0e:9001 Qualcomm / Option SimTech, Incorporated"

ls /dev/ttyUSB*
# Expected: /dev/ttyUSB0 through /dev/ttyUSB4 (five serial ports)

ip link show wwan0
# Expected: an interface named wwan0 (may be DOWN initially)
```

## The "No modems found" gotcha

After a fresh `apt install modemmanager`, `mmcli -L` will often report
`No modems were found` even though the kernel shows the modem attached.
This is because ModemManager only probes for modems at USB hotplug events,
not at daemon startup — so a modem plugged in **before** ModemManager was
installed is invisible.

Fix: restart ModemManager and physically re-plug the dongle.

```bash
sudo systemctl restart ModemManager
# unplug the dongle from USB, wait 3 seconds, plug back in
sleep 10
mmcli -L
```

Expected output:

```
/org/freedesktop/ModemManager1/Modem/N [QUALCOMM INCORPORATED] SIMCOM_SIM7600G-H
```

(The modem index `N` may be 0 or higher depending on prior connections. Use
`mmcli -m any` if unsure — it always resolves to the first available modem.)

## Verify the SIM registered

Insert the SIM (with the dongle unplugged), plug the dongle back in, then:

```bash
mmcli -m any
```

Look for these lines in the output:

- `state: registered`
- `access tech: lte`
- `signal quality: <NN%>` — 30% and above is comfortable indoors
- `operator name:` — should show your carrier (e.g. "Globe Telecom-PH")
- `packet service state: attached`

A `sim-pin2` lock in the Status block is normal for many SIMs; it protects
premium services (fixed-dialing numbers) and does not block data.

## Bring up the data connection

Create and activate a mobile broadband connection profile in NetworkManager.
The APN below is for Globe/GOMO; use your carrier's APN if different.

```bash
sudo nmcli connection add type gsm ifname '*' con-name gomo apn internet.globe.com.ph
sudo nmcli connection up gomo
```

Confirm an IP was assigned and packets flow:

```bash
ip addr show wwan0
# Expected: "inet 100.<x>.<y>.<z>/<prefix>" — Globe's carrier-grade NAT range

ping -c 4 -I wwan0 8.8.8.8
# Expected: 4/4 packets received, latency 25-100 ms after the first packet
```

The first packet is often ~200-300 ms while the modem completes the bearer
setup; subsequent packets settle to the low tens of milliseconds.

## Make it persist across reboots

```bash
sudo nmcli connection modify gomo connection.autoconnect yes
sudo nmcli connection modify gomo connection.autoconnect-retries 0
```

`autoconnect-retries=0` means "retry forever" — after coverage loss the
wearable will keep attempting reconnect indefinitely without manual
intervention.

## Verify WiFi is preferred over cellular

Both networks will be active simultaneously. Confirm the Pi routes through
WiFi when it is available (cheaper, faster) and falls back to cellular only
when WiFi drops.

```bash
ip route show default
```

Expected:

```
default via <wifi-gw> dev wlan0 proto dhcp src <ip> metric 600
default via <cell-gw> dev wwan0 proto static metric 700
```

Lower metric wins. NetworkManager assigns metric 600 to WiFi and 700 to
cellular automatically because it treats mobile broadband as "metered" by
default — no manual configuration required.

## Refresh cycle after a SIM change or carrier change

If the SIM is swapped or the APN changes:

```bash
sudo nmcli connection down gomo
sudo nmcli connection modify gomo gsm.apn <new-apn>
sudo nmcli connection up gomo
```

## SMS

The third capability of the same dongle, used as the emergency fallback
notification path. HTTP alerts to the backend need a working data
connection; SMS rides the cellular control channel and gets through in
marginal-signal conditions that defeat a POST. Driver:
`messaging/mmcli_sms.py`.

### Why `mmcli` and not `AT+CMGS`

The obvious way to send an SMS is an AT command over `/dev/ttyUSB2`. We
deliberately don't.

A serial port carries a single conversation with no notion of multiple
speakers, and **ModemManager already owns those ports** — it maintains
the LTE connection, polls signal, and watches for incoming messages.
Writing AT commands into the same port means two programs interleaving on
one channel, with replies read by the wrong listener. The mild failure is
the SMS silently not sending. The severe one is ModemManager losing track
of modem state and dropping the data connection — killing the internet
the rest of the system depends on, during the emergency that triggered
the SMS.

So we ask the port's owner to send it instead.

### The send sequence

ModemManager models an SMS as an object that is created, then dispatched:

```bash
mmcli -m any --messaging-create-sms="text='hello',number='+639171234567'"
# -> Successfully created new SMS: /org/freedesktop/ModemManager1/SMS/7
mmcli -m any --sms 7 --send
mmcli -m any --messaging-delete-sms=7
```

The delete is not optional housekeeping. The modem stores created
messages in limited memory, so skipping it slowly fills that storage
until `create` starts failing — which would surface much later as
emergency messages silently not being sent. The driver always deletes,
including after a failed send.

### The modem index moves — use `-m any` by hand

Prefer `-m any` in every command you type. ModemManager assigns a fresh
index each time it enumerates a modem, so `-m 0` is correct right up
until a USB glitch, a modem reset or a ModemManager restart, after which
it fails with `error: couldn't find modem` and nothing says why.

The driver cannot use `any` — it needs a concrete index to put in each
`mmcli -m N` call — so it discovers one at startup via `mmcli -L` and
**re-binds when a call reports the modem is gone**. That matters because
discovering only once would mean a wearable up for hours holding a stale
index and failing every emergency SMS for the rest of the session, while
the backend alert kept succeeding and nothing else looked wrong.

The re-bind is reactive, not polled: no background thread, one retry per
call, and only on a stale-handle error. A modem that is genuinely
unplugged costs one extra `mmcli -L` per send and then gives up. See the
module docstring in `messaging/mmcli_sms.py`.

### Verify

```bash
sudo apt install -y modemmanager
mmcli -L                            # lists the SIM7600 and its current index
mmcli -m any                        # needs 'state: registered'
mmcli -m any --messaging-list-sms   # should stay empty between sends
python -m indepensense.messaging.tests.manual.send_sms_test --number +639171234567
```

### polkit authorisation — required, and silent until it isn't

ModemManager guards SMS behind the polkit action
`org.freedesktop.ModemManager1.Messaging`, which upstream defaults to
`auth_admin_keep` — "prompt an administrator for a password". The wearable
has no screen and nobody to prompt, and over SSH the login session isn't
even *active* as far as logind is concerned, so polkit has nowhere to send
the question and denies:

```
error: couldn't create new SMS:
  'GDBus.Error:org.freedesktop.ModemManager1.Error.Core.Unauthorized:
   Unauthorized: PolicyKit authorization failed:
   not authorized for 'org.freedesktop.ModemManager1.Messaging''
```

Every emergency SMS fails this way, and nothing about it is obvious: the
backend alert still succeeds, so the guardian dashboard lights up and only
the text is missing. A full test session ran like this before anyone
noticed.

Install the rule shipped with the repo:

```bash
cd ~/Desktop/thesis/IndepensenseSystem/deploy/polkit
sudo cp 50-indepensense-modemmanager.rules /etc/polkit-1/rules.d/
sudo systemctl restart polkit
```

Then re-run the create command above — a path like
`/org/freedesktop/ModemManager1/SMS/1` means it worked.

The rule grants one unix user the Messaging action only. The username in
it must match `User=` in `deploy/systemd/indepensense.service`; there is
no way to share one value between a systemd unit and a polkit rule, so
changing the account means editing both. See the comments in the rule file
for why this is a narrow grant rather than running the runtime as root.

### Plan requirement

The SIM's plan must permit sending SMS. A **data-only** plan accepts the
create step and fails the send, which looks like a code fault but is not
— confirm by sending a text from the same SIM in a handset. The project's
Globe/GOMO SIM includes call and text.

### What the wearer hears

The spoken response reports both channels, not just the backend. On an
emergency the wearable says "Sending your emergency alert" immediately,
then — once the modem answers — stays quiet if everything worked, or names
what failed: the text, the dashboard, both, or a missing guardian number.
See `telemetry/sms_alerts.py` and the `emergency.delivery.*` messages.

This matters for bring-up: if you hear "Your guardian was notified online,
but the text message did not go through", the polkit rule above is the
first thing to check.

## Troubleshooting

- **SMS create fails with `PolicyKit authorization failed`:** the polkit
  rule is not installed. See "polkit authorisation" above. This is the
  default state of a fresh Pi — it is not a modem or SIM problem, and the
  backend alert succeeding alongside it makes it easy to miss.
- **SMS create succeeds but send fails:** almost always the SIM's plan.
  Verify by texting from the same SIM in a phone. Also check
  `mmcli -m any` shows `state: registered`, not `searching`.
- **`--messaging-create-sms` fails outright:** modem SMS storage may be
  full. `mmcli -m any --messaging-list-sms` then delete the leftovers.
- **`mmcli -L` reports "No modems found":** run the re-plug sequence above.
  If still empty after that, `sudo systemctl status ModemManager` to check
  the daemon is running, and `sudo journalctl -u ModemManager -f` while
  re-plugging to see live probe logs.
- **`nmcli connection up gomo` fails with "Activation failed":** APN
  mismatch. Try `internet` or `gomo` as the APN value.
- **Ping through `wwan0` times out despite registration:** check
  `mmcli -m any` for `packet service state: attached`. If it says `detached`
  the SIM is registered for voice but not data — usually a plan/carrier
  issue, not a Pi issue.

## GPS

The dongle ships **without** the GNSS antenna — only the LTE antenna is
included. An external active GNSS antenna with an SMA connector must be
purchased separately and screwed into the port labelled `GPS` on the
dongle.

### Enable GPS on the modem

By default the GNSS receiver is off. Enable it with an AT command via one of
the AT ports (either `/dev/ttyUSB2` or `/dev/ttyUSB3` works):

```bash
sudo apt install -y minicom
sudo minicom -D /dev/ttyUSB2 -b 115200
```

Inside minicom (turn off local echo with `Ctrl-A` then `E` if you cannot see
what you type):

```
AT+CGPS=1
```
→ Expected reply: `OK`.

```
AT+CGPS?
```
→ Expected reply: `+CGPS: 1,1` (enabled, standalone mode).

Exit minicom with `Ctrl-A` then `X`.

### Make GPS auto-start on boot

Otherwise `AT+CGPS=1` has to be re-issued after every modem reboot. One-time
persistent setting via the same minicom session:

```
AT+CGPSAUTO=1
```
→ Expected reply: `OK`. GPS now starts automatically whenever the modem
powers up.

### Verify the raw NMEA stream

Before running the Python driver, confirm sentences are actually flowing:

```bash
sudo cat /dev/ttyUSB1
```

Expected: continuous lines of `$GNRMC`, `$GNGGA`, `$GNGSV`, etc. Indoors the
`$GNRMC` fields will show `V` (void — no fix); outdoors they change to `A`
(active) within 30-60 seconds of clear-sky exposure. Ctrl-C to stop.

Nothing on the stream, or garbled characters, points to a hardware issue:
antenna not seated firmly in the SMA port, or `AT+CGPS=1` was not accepted.

### Measured performance on the wearable

Field-tested outdoors in Lipa, Philippines, with a clear view of sky:

| Metric | Value |
|---|---|
| Cold-start time to first fix | ~30 seconds |
| Satellites in view (typical) | 8-9 |
| HDOP | 0.6 (excellent — geometry is good) |
| Position stability while stationary | ±1 in the 6th decimal (~10 cm jitter) |
| Altitude accuracy | ±20-30 m (normal for standalone GPS) |
| Fix quality | 1 (standard GPS, no augmentation) |

Indoors, no fix is expected. This is normal — GPS signals do not reliably
penetrate roofs. The wearable's use case is outdoor navigation, so this is
not a limitation.

### Python driver

See `src/indepensense/sensors/gps.py`. The `SIM7600GPS` class opens
`/dev/ttyUSB1`, reads NMEA lines, and merges `$GxRMC` + `$GxGGA` into a
single `GPSFix` dataclass on each `.read()` call.

Manual test:
```bash
python -m indepensense.sensors.tests.manual.single_gps_test
```
